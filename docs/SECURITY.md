# 認証・認可設計と制約

## 信頼境界

ブラウザー → `portal` Edge Function → service_role限定`public.portal_api` → 非公開`portal_private`スキーマという経路です。ブラウザーからDBテーブルへ直接アクセスできません。Supabase Auth JWTと独自セッションを混在させません。APIのaction allowlistにbootstrap、汎用SQL、管理者作成機能はありません。

一般ユーザーと管理者は別テーブル、別ログインaction、別セッションprincipalです。ユーザーの`player`/`uploader`権限は管理権限へ昇格できません。保護操作では入力のrole・admin IDを信用せず、DBからprincipal/status/BAN/期限/失効状態を読みます。現段階の`admin`と`super_admin`は同じユーザー管理操作が可能です。管理者の追加/編集はどちらにも公開していません。

## パスワード

- PostgreSQL pgcryptoのbcrypt、cost 12、ランダムsalt。5文字以上、UTF-8で72バイト以下を強制し、bcryptの切り捨てを防ぎます。パスワードのtrim/小文字化はしません。
- ユーザー名はtrim + ASCII小文字化。`a-z0-9_`の3〜32文字、DB一意制約。ユーザー名の推測/列挙を完全に隠す設計ではありません。
- 本人用1件、代替は0〜5件。本人変更時は本人用行のみ置換し、全セッションを失効。代替行は維持します。
- 本人用パスワード変更には本人用の現パスワードが必要です。代替だけを知っている人は本人用パスワードを上書きできません。ただし代替は同じユーザーとしてログインできるため、ユーザー名変更など一般のアカウント操作は可能です。
- 代替削除は即時に照合対象から外し、そのパスワードによるセッションも失効。本人用は管理画面から削除できません。
- パスワード/ハッシュを応答、監査ログ、consoleへ出しません。管理者へ返す代替情報はID・ラベル・作成日時だけです。ラベル/理由へ秘密情報を手入力しないでください。
- パスワードはHTTPSでEdge→DBへ渡り、DB内でハッシュ化します。DB所有者はサーバーを信頼する必要があります。SQLパラメーター/HTTP bodyのデバッグログやリクエスト記録を有効にしないでください。

## セッションと競合

Web Cryptoの暗号学的乱数32バイトからトークンを作り、HMAC-SHA-256（server-only pepper）だけをDBへ保存します。ブラウザーは`X-Portal-Session`で送ります。cookieを使用せず、CORSはorigin完全一致、レスポンスは`no-store`です。CORSは認可の代替ではありません。originなしのCLIリクエストも同じセッション検証を通ります。

ログイン・認可・管理操作はDBトランザクション内で対象ユーザー行をロックします。保護操作はprincipalを特定→行ロック→セッション再読み込みの順です。これによりBAN/KICKと競合した処理が、失効前に読んだセッションだけで実行を続けることを防ぎます。BAN前に完了した操作を遡って取り消すことはできません。今後の投稿操作も同じトランザクション境界の認可を利用し、先に`user.me`だけを呼んで認可済みとみなさないでください。

Rate limitはDBのatomic upsertで実装し、失敗応答を例外にせずカウンターを確定します。管理者/一般ログインで予算を分離します。全体カウンターはトランザクション中ロックされるためログイン処理を直列化します。小規模運用向けで、高負荷環境には適していません。存在しないユーザーでもdummy bcryptを行いますが、代替パスワード数による時間差は残ります。分散攻撃や利用妨害を完全には防げず、公開規模を拡大する前に信頼できるIP取得・分散rate limiter・CAPTCHA等を設計してください。

## 公開ゲームと管理画面のorigin

現在のGitHub Pages版はゲームHTMLと管理画面が同一originです。localStorage/sessionStorage/cookieにトークンを置かないことで永続ストレージからの窃取を避けますが、**悪意ある同一originのゲームから管理画面を完全隔離することはできません**。同一originのwindow参照やService Workerもリスクです。現段階では所有者が信頼する既存ゲームだけを公開してください。

第三者ZIP公開のPhase 3/4へ進む前に、ゲームの配信を別originへ分離し、管理originに未信頼HTML/JSやService Workerを配信しない設計が必須です。管理画面のプレビューでZIP内HTMLを直接実行しません。追加ページのCSPとtextContentによる描画は追加防御であり、同一origin問題の解決ではありません。

## 監査・秘密・復旧

監査は管理者ID、action、対象ID、時刻、許可したmetadataだけです。通常APIに編集/削除機能を設けず、DBトリガーでUPDATE/DELETE/TRUNCATEも拒否します。DB所有者はトリガーを変更できるため、所有者まで含む改ざん防止/WORM保管ではありません。

`.env*`をignoreし、公開ビルドはallowlist方式です。service_role JWTを公開設定へ指定するとビルドが拒否します。pepperローテーションでは旧セッションがすべて使えなくなります。service_roleやGoogle secretが漏れた場合は各サービスで失効・再発行し、DB監査とセッションを確認します。Gitからファイルを削除するだけでは秘密は失効しません。

テストは実SQLとHTTP境界を検証しますが、第三者セキュリティ監査・本番負荷試験を実施済みという意味ではありません。Supabase実環境の疎通は所有者設定後に行います。
