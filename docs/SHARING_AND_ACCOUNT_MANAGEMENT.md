# アカウント指定の共有と管理

## ゲームを特定の人へ共有する

共有相手の「アカウント」画面のアカウントID（UUID）をコピーしてもらいます。投稿時または管理・編集の公開設定で「アカウント指定で共有」を選び、そのIDを改行またはカンマ区切りで指定します。1〜50人、有効な一般ユーザーのみ、重複・本人・管理アカウントのIDは指定できません。ユーザー名や表示名を変更してもIDは変わりません。

共有ゲームは公開一覧に出ません。一般投稿者は承認後、信頼済み投稿者は審査省略後、公開日時を過ぎた時点で相手の「アカウント → 共有されたゲーム」に表示されます。共有相手はログインしてプレイします。URLを転送しただけでは指定外の人は閲覧できません。相手の削除・共有解除・BAN・無効化は次のアクセス時から反映されます。すでに端末へ読み込まれたデータは回収できません。

下書き・限定公開・公開も引き続き利用できます。公開範囲を共有以外へ変更すると共有相手の関連を削除します。投稿者本人は従来の自分だけのプレビューも利用できます。

## 管理画面

ユーザー一覧に一般ユーザーと管理アカウントを表示します。通常の管理者は一般ユーザーとゲームを管理できます。管理アカウントの作成・名前変更・パスワード変更・権限変更・KICK・無効化・有効化・完全削除はsuper adminのみ操作できます。自分自身の権限変更・無効化・削除は禁止し、最後の有効なsuper adminを失う操作もDBで防ぎます。パスワード・権限変更、KICK、無効化時は既存の管理者セッションを失効させます。

ゲームの完全削除とアカウントの完全削除は「確認 → 対象名の入力」の二段階です。アカウント削除時には全投稿ゲーム、パスワード、代替パスワード、セッション、他のゲームへの共有関連を削除します。削除後の投稿URLは閲覧できません。下書きも管理者の一覧に表示して削除できるようにしますが、下書きのダウンロード・審査は許可しません。

監査ログは要件に沿って削除せず、操作した管理者のUUIDと操作内容を残します。管理者削除時も過去ログを維持するため、監査ログの管理者外部キーだけを解除しています。認証情報はログに記録しません。

## ファイル削除と再試行

game_filesに現在・過去のZIP、Driveファイル、サムネイルを記録し、ゲームやアカウントを削除するとsubmission_deletions / deleted_game_filesへ削除対象を移します。外部保管先を操作する前にDBからゲームを削除して閲覧を止めます。成功した保管ファイル削除だけを完了扱いにし、失敗時はキューを残します。

管理画面の「保管ファイルの削除を再試行」で10ゲームずつ処理します。大量削除時や外部障害時は繰り返してください。表示される「削除が残っています」は閲覧権限が残っている意味ではありません。CLIでも安全なサーバー環境で既存のscripts/cleanup-deleted-submission.mjsに削除済みゲームUUIDを渡して再試行できます。実際の秘密情報はローカルの環境変数等を使い、Gitに入れません。

導入時には既存の現在のファイルを記録します。過去にDBへ記録されずアップロード途中で残った孤立ファイルは、この機能だけで自動的に識別できません。手動整理の際は現行DB参照と削除キューを確認してください。

## DBと権限

既存migrationの後に202610040018_package_replacement_tag_limit.sql、202610050019_account_sharing_and_management.sqlを順番に適用し、最新Edge Function portalをデプロイします。

game_shares(game_id,user_id)は複合主キー、非公開スキーマ、RLS有効、ブラウザー用ロールから直接アクセス不可です。共有先を編集できるのは投稿者本人です。shared-game / shared-packageのEdge APIは毎回セッション、BAN、状態、共有先、承認、公開日時をDBで検証し、Storageキー・Drive ID・共有先一覧を閲覧者へ公開しません。user.shared.game、ストレージ削除、内部ファイル管理関数は通常のJSON APIから呼べません。管理者権限はサーバー側で判断します。
