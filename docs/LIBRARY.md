# いいね・個人リスト・フォロー

投稿されたゲームには「いいね」「リストに保存」「作者をフォロー」があります。プレイ専用ユーザー、通常ユーザー、管理アカウント、全権管理アカウントが利用できます。従来の `games.json` にあるサンプル作品は対象外です。

## 利用方法と非公開情報

- **いいね**: ゲームページで切り替えます。件数だけが閲覧者に表示されます。押した人の一覧・アカウントIDは作者にも管理者にも表示されません。本人のライブラリの「いいねしたゲーム」に自動保存され、解除すると外れます。この履歴は共有できません。
- **リスト**: ゲームページから複数の名前付きリストに保存できます。ライブラリで作成・名前変更・検索・上下の並べ替え・項目の削除・リスト削除ができます。リスト削除はゲーム本体を削除しません。
- **共有**: リストは既定で本人専用です。「共有リンクを作成・コピー」を明示的に押すと共有されます。URLを知る人は読み取りだけ可能です。本人のアカウント名は共有ページに載りません。「共有を停止」で旧URLを無効化し、次回の共有では別のURLを生成します。リンクは転送可能なので共有相手を選んでください。
- **フォロー**: ゲームページから作者をフォローできます。本人のみ「フォロー中」でフォロー先とその作者の最近の12作品のうち閲覧できる作品を確認できます（25人ずつ表示）。フォロワー一覧、フォロワー数、他人のフォロー先一覧を返すAPIはありません。
- **閲覧権限**: 保存・共有・フォローによってゲームの閲覧権限は増えません。共有停止、下書き変更、予約公開、グループ脱退・無効化などがあれば、その後の要求ではゲーム名やURLも返さず「閲覧できない作品」と表示します。作者自身の非公開作品は本人の編集・プレビューへリンクします。ゲームを削除するといいね・リストの関連も削除します。

## DBと認証

追加migration: `supabase/migrations/202610090024_social_library.sql`。既存migrationを編集せず、023の後に一度だけ適用します。

| テーブル（portal_private） | 用途 |
| --- | --- |
| game_likes | ゲームと本人の関連。user_id / admin_id のどちらか一つ、ゲームとの複合UNIQUE |
| game_playlists | 本人の名前付きリスト。48桁のランダム共有トークンは初期状態NULL |
| playlist_items | リストとゲームの関連。複合UNIQUE、sort_orderによる順序 |
| creator_follows | 本人と作者の関連。複合UNIQUE、自分自身はフォロー不可 |

全テーブルでRLSを有効化し、anon/authenticated/service_roleに直接アクセスを許可しません。既存のsecurity definer RPCが有効なユーザーまたは管理者セッションを毎回検証します。一般の管理・全権管理アカウントにも他人の個人ライブラリを閲覧・変更する経路はありません。DB所有者の運用アクセスはアプリの管理アカウントとは別です。

ゲームごとの「social.game」は件数と現在の本人の状態だけを返します。「social.list.shared」は共有トークンと各ゲームの現在の閲覧権限を検証します。この2つだけ匿名読み取り可能です。無効なセッションを匿名に切り替えて認証を回避することはありません。

`social.likes`、`social.following`、`social.lists`、`social.list.get/create/update/delete/item/order/share`、`social.like/follow` は本人の有効なセッションが必須です。クライアントのuser_id/admin_idは権限判定に使いません。アカウント行とリスト行のロック、UNIQUE、外部キーで重複や競合を制御します。順序変更は現在の全項目IDを重複なく指定する必要があり、欠落・別リストのIDは拒否されます。

上限は本人あたりいいね1,000作品、リスト50個、1リスト500作品、フォロー500人。匿名APIでいいね履歴・フォロー履歴は取得できず、BAN/KICK/無効化で本人向け操作が停止します。BAN・無効化されたリスト所有者の共有URLも利用できません。アカウントの完全削除でその本人の関連はCASCADE削除します。

## 反映・検証

1. SQL Editorで024を適用。
2. Edge Function `portal` を更新（security.mjs / handler.mjs の新しい許可アクションを含む）。秘密情報の追加は不要。
3. テストとビルドを通し、mainへ反映してGitHub Pagesを更新。

`node --test tests/*.test.mjs`、`node scripts/build-site.mjs`、`npm run test:browser` で検証します。SQL/Edgeの所有権、匿名読み取り、共有失効、履歴非公開、削除とRLS、実際のSQLに接続したブラウザーの保存・フォロー・共有・並べ替えを確認します。本番のアカウント・投稿にテスト用データを作る必要はありません。
